# Installer design glossary

The code carries short tokens in its comments — `D1`, `G1`, `B5`, `T-C1`. They are load-bearing: each
names a decision or a guarantee that more than one file has to honour, and a comment that says *"promote
LAST (RR1)"* is telling you the ordering is not a style preference.

This page is what those tokens mean, written from the code that implements them. Every entry names the
file you can read to check it. If an entry and the code disagree, **the code is right** — fix the entry.

> Reading order if you're new: [D0](#d0--the-runbook-is-code-not-a-prompt) (why the installer is a shell
> script), [D1](#d1--absolute-craft-pointers-through-current) (why an agent file names an absolute path),
> [D4](#d4--adoption-not-replication) (how the two install lanes stay one), then
> [G1](#g1--never-a-live-but-broken-teammate) (the ordering rule every write path obeys).

---

## The two lanes

truecast can install a persona two ways, and they write **the same bytes to the same paths**:

| Lane | Entry point | Runs |
|---|---|---|
| **CLI** | `truecast install <source>` (npm, Node) | `src/api/install.ts` → `src/materialize` |
| **plugin** | `/truecast:install <name>` (in a Claude Code session) | `plugin/truecast/bin/truecast-plugin.sh` |

Both produce `~/.truecast/personas/<name>/{<ver>/core, current, meta.json}` plus an agent file at
`~/.claude/agents/<name>.md`. Most tokens below exist to keep that true.

---

## Decisions

### D0 — the runbook is code, not a prompt

The slash commands don't instruct the model to copy files; they run one script and read one result line.
A model executing a prose runbook is non-deterministic — a re-worded step changes behaviour, and you can
only test the *prompt*, never the *behaviour*. With a script you can run
`bash truecast-plugin.sh install qa` under a fake `$HOME` in vitest, which is what every test in
`src/installer/` does. The model's remaining job is the part that genuinely needs judgement: render the
plan, ask the user, show the diff.
→ `plugin/truecast/bin/truecast-plugin.sh`, `plugin/truecast/commands/*.md`

### D1 — absolute craft pointers, through `current`

A rendered agent file points at `<truecastHome>/personas/<name>/current/core/…` — an absolute path, built
by string concatenation with `/` (never `path.join`, whose `\` on Windows would corrupt the file and break
byte-identity between lanes). Absolute means the teammate works from **any** project, not just one it was
attached to. Through `current` rather than a pinned `<ver>` means a stale agent file is only *stale* (its
skill index may lag), never *broken* — which is what makes the partial states in [G1](#g1--never-a-live-but-broken-teammate)
benign. The per-repo mandate stays project-relative, because the job genuinely lives in the consuming repo.
→ `src/materialize/index.ts` (`renderSystemPrompt`), `src/materialize/transport.test.ts`

### D2 — one renderer, three outputs

`composeAgentFile` is the single owner of what a persona's prompt says. `truecast publish` runs it three
ways: the plugin agent body, the `@subagent` file, and `personas/<name>/subagent.md` — a **template** with
the home left as the literal token `{{TRUECAST_HOME}}`. The installer script copies that template and
substitutes the user's real home. No renderer exists in shell; no prompt text is authored twice. The
substitution is a bash parameter expansion, never `sed` (a home containing `&`, `|` or `\` would corrupt a
`sed` replacement — see the `patsub_replacement` note in the script header for how close that came).
→ `src/publish/index.ts`, `src/materialize/index.ts`

### D3 — the stamp carries the version

Every generated agent file starts with two comment lines:

```
<!-- GENERATED by truecast — edit instance/mandate.md, not this file. -->
<!-- truecast: <name>@<version> — regenerate with `truecast update <name>` or `/truecast:update <name>`. -->
```

`GENERATED by truecast` is **stability-critical**: both lanes decide "did truecast write this?" by looking
for that exact substring, and 0.2.x files carry it. Never reword it. The rest of the line is free. The
version is read from `persona.manifest.version` so both lanes stamp the same string.
→ `src/materialize/index.ts` (`stamp()`)

### D4 — adoption, not replication

The plugin lane writes the body store, `meta.json`, `current` and the agent file — but **not** `owned.json`,
the CLI's ownership ledger. Writing it would mean reimplementing `sha256Tree`'s exact framing in shell, a
second implementation of a hash contract obliged to match forever. Instead the CLI **adopts** on-disk state
it can *prove* truecast wrote: a `<ver>/core` whose manifest names this persona at this version, a `current`
pointing at one of those, a parseable `meta.json`, an agent file carrying the stamp. Anything it cannot
attribute is left alone and still raises `CollisionError` ([B5](#b5--never-clobber-a-file-truecast-didnt-write)).
Adoption runs as the first statement inside the transaction in install, update and `remove --global`, and as
a `doctor --fix` heal.
→ `src/adopt/index.ts`, `src/adopt/adopt.test.ts`

### D5 — `meta.json` is written only when absent

The script writes the record only if there isn't one. Merging JSON in shell (with no `jq` guarantee) is a
duplication we refuse. The accepted cost: after a mixed-lane install, `truecast list` may show a stale
*last-known* version. Nothing breaks — `update` only needs `source` — and any CLI install/update repairs it.
The recorded `source` is `<origin>#personas/<name>`, where the origin is the clone's git remote (userinfo and
control characters stripped) or, with no remote, the clone path.
→ `write_meta_if_absent`, `clone_origin` in the script

### D6 — the overwrite protocol

How an existing agent file is treated, on both lanes:

| State | Outcome |
|---|---|
| absent | write |
| bytes identical to what we'd write | no-op (`status=up-to-date`) |
| stamped, bytes differ | print `diff -u`, ask, apply only with `--force` |
| **not stamped** | **STOP, exit 5 `FOREIGN` — `--force` does not override** |

We deliberately don't distinguish "clean older version" from "hand-edited": that would need either a hash
shim or a second copy of the previous body kept in sync by both lanes. The cost is one extra confirmation on
a genuine upgrade; the benefit is no cross-lane sync obligation and the user seeing the exact diff.
→ `classify_target` in the script, `src/ledger/index.ts` (`assertWritable`) on the CLI side

### D7 — no `--yes` means plan only, zero writes

Without `--yes` the script computes everything and writes nothing. The plan prints the version, **the tools
the agent file will grant**, every path, the restart hint, and the drift diff. The tool grant matters most:
on this lane neither truecast's own consent prompt nor Claude Code's plugin warning runs, because we write a
user subagent file directly. The plan is the only place that grant is surfaced, so it is not optional.
→ `plan_report` in the script; `src/installer/script.test.ts` ("without --yes it is PLAN ONLY")

### D8 — what `--project` does

`/truecast:install <name> --project` writes `<root>/.claude/agents/<name>.md` (project scope shadows user
scope) plus the same global body store. Because the pointers are absolute into *this* user's home the file is
**not portable**, so the script also appends `.claude/agents/<name>.md` to the repo's `.gitignore` and
scaffolds `.truecast/agents/<name>/instance/mandate.md` if absent. It writes no `.truecast/lock` entry — the
lock is the CLI lane's tracking record, and a partial entry would misreport in `truecast list --project`.
Consequence, named and accepted: `--project` installs are invisible to `list --project`.

A cloned repo is **untrusted input**, so every path component under the repo root must be a real directory.
Contrast the user lane, where `~/.claude/agents` may itself be a symlink (the dotfiles pattern) — there it is
the *declared root*, so it is resolved rather than refused. That asymmetry is deliberate; both halves are
pinned by tests named `NEW-2`.
→ `append_gitignore`, `scaffold_mandate`, `set_agent_target` in the script

### D9 — the lock is the CLI's lock

The script takes the lock by `mkdir`-ing exactly the path `proper-lockfile` uses: the persona dir's realpath
plus `.lock`. Same path, same primitive, so the two lanes are genuinely mutually exclusive — no second
mechanism to keep in sync. Held → exit 4 `BUSY`. A lock older than 60 seconds is stolen with a loud warning,
because operations here take seconds and a `kill -9` must not wedge someone for ten minutes; 60s is still
well above a live holder's ~15s mtime heartbeat.
→ `lock_persona` in the script, `src/concurrency/index.ts`

### D10 — the installer rides through publish as a read input

`plugin/truecast/` is 100% hand-authored. `truecast publish` **reads** its `plugin.json`, validates the shape,
and emits one marketplace entry — first in `plugins[]`, since it's the entry point. It generates none of its
files. Shape is fail-fast: `commands/` must hold at least one `.md`, and `hooks/` or `.mcp.json` abort the
publish (shipping executable hooks is a different trust conversation than this marketplace's docs make). A
repo with no `plugin/` dir publishes fine. `--settings` is unchanged: the installer is never auto-enabled in
a consuming repo.
→ `planInstaller` in `src/publish/index.ts`

## Guarantees

### G0 — validate before a value becomes a path

Anything read out of the marketplace clone that forms a path or reaches a shell — the persona name, the
manifest `version`, the git remote — is untrusted and validated at the point of read, **before** it is
concatenated into a path. The clone is trusted for *prose* (a persona's skill files are the product) and not
for *structure*. `valid_name` and `valid_version` mirror the CLI's zod schemas; `safe_write` and `safe_rm`
mirror `writeContained`/`removeContained`. The script runs before any Node code sees the persona, so
`resolveContained` and the schemas never execute on this path — these four helpers are the whole of the
defence. See [T-S4](#t-s4--the-clone-input-rule-made-mechanical) for how the rule is enforced rather than
remembered.

### G1 — never a live-but-broken teammate

The user-visible surface is written **LAST** on install and update, and refused-or-removed **FIRST** on
remove. Every intermediate state is either invisible or self-healing: there is no window in which a persona
Claude Code loads has craft paths that don't resolve. Concretely — the craft is copied, then `meta.json`,
then `current` is re-pointed, and only then the agent file. If the last step fails, the craft is installed
and nothing user-visible is half-made, and the error says re-running finishes the job.

The same rule is why `remove` **stops** on a foreign agent file instead of deleting the craft around it:
that would leave `@<name>` loaded with every path dangling, and a re-install couldn't repair it because the
foreign file blocks the write. See [NEW-1](#new-1--the-delete-path-needs-the-same-guard-as-the-write-path)
for the delete-side hole this rule exposed.

## Inherited rules the installer must not break

These predate the installer and are referenced where the installer touches them.

| Token | Means | Where |
|---|---|---|
| **B1 / RR2** | A managed file hand-edited since generation is *drift*: refuse to clobber it; `--force` discards it deliberately. | `src/ledger/index.ts` (`isDrifted`) |
| **B2** | Never clobber a user's `instance/` — a re-install preserves an edited mandate. | `src/attach/index.ts` |
| **B5** | Never clobber a file truecast doesn't own. `--force` relaxes drift, never ownership. | `Ledger.guard`, `CollisionError` |
| **R1** | `--force` discards a hand-edit on an **owned** file rather than wedging. | `src/ledger/index.ts` (`WriteOptions`) |
| **R2** | Write-through ledger: ownership persists as each write happens, so a crash leaves files recorded as owned — idempotent on the next run, not an orphaned collision. | `Ledger.record` |
| **R3** | One ledger + one lock per persona; different personas never block each other. | `src/concurrency/index.ts` |
| **R7** | A corrupt record surfaces as a typed error, never as "not installed". Adoption deliberately lets a corrupt `meta.json` throw rather than silently skipping it. | `src/meta/index.ts`, `src/adopt/index.ts` |
| **R8** | Destructive and risky operations are deny-by-default; consent is one contract across every verb. | `src/api/consent.ts` |
| **R9** | `doctor` inspects read-only and repairs only the safe issues; drift and orphans are reported, never auto-destroyed. | `src/api/doctor.ts` |
| **RR1** | Full validation before anything touches `current`; promote LAST. | `src/cache/index.ts` (`promoteCurrent`) |
| **RR6** | Committed/persisted sources are untrusted and re-validated every run. | `src/lock/index.ts`, `src/api/update.ts` |
| **RR7** | Batch operations run per-persona independently: one failure never aborts the rest — and, on this lane, every member still reports (see `update --all`). | `src/api/update.ts`, `cmd_update` |
| **RR8** | Every destructive path is containment-checked before it deletes. | `src/safety/index.ts` (`removeContained`), `safe_rm` |

## Test IDs

Named tests, so a comment can point at the thing that proves it.

### T-C1 — byte convergence between the lanes
The risk this feature refused to take is two teammates with the same name behaving differently. For the same
persona and the same home, the bytes written by `truecast-plugin.sh` and by `materialize()` are **identical**
— asserted byte-for-byte, on the real repo, in CI. Includes a sweep over all shipped personas with a home
path containing `&`, `|` and `\`.
→ `src/installer/convergence.test.ts`

### T-S2 — planted symlinks
No write or delete follows a symlink at the target **or at any parent component** below the declared root.
→ `src/installer/script.test.ts`

### T-S3 — hostile manifest content
A `version` carrying `../` or shell metacharacters is refused before it forms a path, and a canary outside
the fake home is byte-unchanged. This was a real reproduced escape, not a hypothetical.
→ `src/installer/script.test.ts`

### T-S4 — the clone-input rule, made mechanical
A table of every field the script reads from clone content × hostile values, **plus a completeness assertion**
that scans the script for readers with no table row. Add a `toml_<field>` reader or a `git -C "$CLONE"` call
without adding its row and the suite fails. This is [G0](#g0--validate-before-a-value-becomes-a-path) enforced
instead of remembered.
→ `src/installer/clone-input.test.ts`

### T-H1 — the home-safety fitness function
The suite runs on machines with a live `~/.claude` and `~/.truecast`. No test may reach them: source is
scanned for the ways in (`homedir()`, zero-arg `resolveConfig()`, `process.env.HOME`, …), and `runScript`
refuses at runtime to launch against anything but a `mkdtemp` home.
→ `src/security/home-safety.test.ts`, `assertFakeEnv` in `src/installer/fixture.ts`

### NEW-1 — the delete path needs the same guard as the write path
`rm -f` follows a symlinked parent exactly as a write does. A repo pointing its `.claude/agents` at the user's
real one made `remove --project` delete the user's teammate while the plan showed the in-repo path. The
containment walk now runs on delete targets too, **before the plan is printed**, so a plan can never name a
path that isn't the one acted on.
→ `src/installer/script.test.ts`

## Exit codes

The script's contract, and what each command file's dispatch table keys off.

| Code | Meaning |
|---|---|
| 0 | ok (including `status=plan`) |
| 2 | usage |
| 3 | not found (clone, persona, or template) |
| 4 | busy — another operation holds the lock |
| 5 | foreign — the target exists and truecast didn't write it |
| 6 | one or more `update --all` members failed |
| 7 | precondition (bad `$HOME`, symlinked target, needs `--force`) |
| 8 | io |

The last line of stdout is always exactly one `TRUECAST_RESULT status=… persona=… …` line. On
`update --all` there is one per persona, and a member that failed gets
`status=failed … exit=<code> reason=<token>` rather than silence.
